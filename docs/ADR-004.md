# ADR-004：工程文档与验证证据分层

- 日期：2026-10-15。
- 状态：本轮采用，仅约束本文档包和交付表达。
- 范围：仓库地图、集成、契约、测试、性能、部署及安全说明。

## 背景

仓库同时有源码、合成验证、历史采集、专题交付和正在修改的工作树。单独看到文件、测试通过或历史报告，很容易错误推断当前设备、部署和整车已经可用。

本轮可以在 Windows 验证确定性 Python 行为，但无法替代 Jetson 构建、真实 ROS 图和现场运动。用户要求完整工程文档，而不是制造新的实机通过证据。

## 决策

1. 在 docs 根目录提供统一入口，保留已有 architecture、dg202611 和 protocol 专题，不批量迁移历史内容。
2. 每份文档注明核对日期、源码依据和验证限制。
3. 使用 LOCAL_ONLY、TARGET_WRITTEN、TARGET_VERIFIED、REMOTE_VERIFIED 和 NOT_PROVEN 表达范围，逐项关联真实证据。
4. 未执行步骤、缺依赖、空数据和人工测试骨架不得标通过。
5. 历史证据保留原日期，不自动升级为本轮验收结果。

## 考虑过的选择

| 方案 | 未采用原因 |
| --- | --- |
| 把全部信息写进主 README | 操作风险、历史结论和接口细节混在一起，难维护 |
| 批量搬迁并重写旧文档 | 引用易失效，也会覆盖其他未提交工作 |
| 只写计划，不记录当前实现 | 无法支持真实对接与审阅 |
| 用单元测试替代端到端结论 | 无法证明驱动、时序、TF、网络和现场行为 |

## 影响

优点是每种完成结论都有清楚边界。代价是发布时必须补目标机和现场记录，不能靠一个“通过”覆盖整个系统。

文档不是自动生成的最终事实源。接口变更仍需人工核对源码与行为，发现冲突以真实代码和当前运行证据为准，同时修正文档。

## 验收与失效条件

- 文档互相引用存在，源码入口可定位，受保护旧文件未覆盖。
- 定向测试结果和尚未执行项均写入变更说明。
- 新增远端或实机证据时，须附采集时间和对象，才允许更新相应状态。

若后续更改状态体系、证据门槛或交付目录，应新增决策，而不是静默重新解释旧标签。
