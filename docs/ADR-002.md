# ADR-002：以配置来源和接口契约约束集成，而非批量改参数

- 日期：2026-10-15。
- 状态：采纳；本轮只补配置清单与评审规则，不改实机配置。
- 范围：ROS 参数、launch 选择、环境变量、地图路线身份与外部接口。
- 关联：[集成规格](INTEGRATION_SPEC.md)、[接口契约](API_CONTRACT.md)、[技术债](../TECH_DEBT.md)。

## 背景与问题

本仓库的配置并不集中在一个文件。设备选择来自 bringup 参数；定位、导航和几何分布在 YAML、URDF 与行为树；桥接有 ROS 参数；云客户端直接读取环境变量；部分业务配置还支持特定环境覆盖。目标工作空间的默认路径包含 /home/nvidia/ros2_DL，而当前源码在 Windows。把路径能否存在、参数是否有默认值和真实部署是否成功混为一谈，会导致文档看似完整，但换一台机器就无法复现。

地图和路线也不是“名字一样就能配套”。地图图像、YAML、分辨率、原点、尺寸和内容摘要共同影响路线的含义。显示用缩略图与原始地图不在同一像素尺度。若重构时只追求统一字段或简化判断，可能让预览坐标被当作真实坐标，或把不同地图的路线错装到一起。

此外，默认桥接监听所有网卡，本地令牌默认未启用。这个事实需要明确说明，但不能在没有部署上下文时擅自改全局网络、服务或真实密钥。文档需要告诉维护者哪里必须配置，不能把默认值包装成已经加固的状态。

## 决策

采用“记录来源、保留原契约、验证不变量”的方法。集成规格按配置所属模块列出来源、默认值、单位与边界；仓库地图列出所有 ROS 包声明。默认值只能解释源码意图，发布记录必须另记实际生效值，敏感值只记是否配置，不复制内容。

不建立一个声称可以覆盖全部配置的总开关，也不把环境变量优先级泛化到所有 YAML。云客户端按自身读取逻辑生效；ROS 节点按参数声明、launch 和参数文件生效；平台存储和三维目录覆盖按对应实现判断。涉及优先级的文档必须指向实际读取位置。

对配置回归优先约束不变量，例如坐标系一致、地图未知语义不变、局部与全局几何相容、控制输入和最终输出分离、单位明确、数值有限且处于合法范围。只有安全阈值和外部文件协议才应锁定精确值；不把普通调参和界面文案写成容易误报的断言。

本轮在离线评估中统一匹配距离验证：单帧对与汇总入口都要求有限正数，避免同一个参数在不同调用入口含义不同。该调整只影响非法输入，不改变有效输入的统计公式，也不修改 ROS 参数、地图或导航行为。

## 考虑过的方案

方案一是把所有参数搬入一个总 YAML。它看起来便于阅读，但可能绕开上游驱动默认值、ROS 参数命名空间和已有部署脚本，还需要处理环境中的真实凭据。迁移成本和回归面远高于本轮需求，因此不采用。

方案二是把目前观察到的每个数值直接写进测试，任何变化都报错。它能产生很多“保护”，但普通调参、界面展示和运行目录差异都会让检查失败。维护者最终可能习惯忽略失败，真正的安全变化反而不醒目，因此拒绝。

方案三是保留已有配置结构，补来源索引和契约说明，只修确定性边界错误，再由目标机验证最终参数。它要求文档和代码同步维护，但不会无意改变现场系统，因此采纳。

## 后果与维护要求

正面结果是排障可以先区分“配置写在哪里”“实际读取哪份”“目标机最终值是什么”。本地离线通过不会被误认为设备路径、CAN 速率或 SDK 已经正确。地图预览、地图文件和部署身份被作为不同对象追踪，减少只凭文件名判断兼容性的风险。

代价是默认值表会随实现漂移，因此接口或配置改动必须同步更新来源表。包声明存在依赖不等于已经安装，声明遗漏也不能用本次静态表证明不存在。条件依赖需要按目标 ROS 版本解析，上游 SDK 的版本关系仍应从实际安装与构建记录确认。

本轮不会自动安装依赖、修改系统服务、开启公网监听、写入令牌或修复所有硬编码路径。技术债记录的是后续需要处理的边界，不是授权执行这些操作。

## 验收与撤销条件

本轮检查应能从文档找到每个主要配置来源，并且有效匹配数据的离线结果保持一致。新增非法参数和格式混用案例必须得到明确错误，而不是成功报告。

现场发布需要核对实际参数、地图摘要、工作目录、监听地址、认证状态和设备映射，涉及运动的验证由现场人员执行。若未来决定集中配置，应先列迁移映射、默认兼容规则、敏感值处理和可用的回滚文件；没有迁移验收前，不删除原配置入口或让多份配置竞争生效。
