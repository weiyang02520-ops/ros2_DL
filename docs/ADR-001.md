# ADR-001：保持分层集成与唯一运动控制边界

- 日期：2026-10-15。
- 状态：采纳为本轮整理和后续评审约束；记录既有设计，不表示完成新的实机架构部署。
- 范围：驱动、定位导航、任务、交互、桥接与独立感知的责任边界。
- 关联：[集成规格](INTEGRATION_SPEC.md)、[仓库地图](REPO_MAP.md)、[运动测试边界](../skills/robot-motion-test-boundary/SKILL.md)。

## 背景与问题

本仓库不是一个可以在普通电脑直接启动的单体程序。它同时包含 C++ 硬件驱动、Python ROS 节点、导航与定位参数、Qt/QML 界面、HTTP 桥接、云端连接、视觉处理和离线实验工具。这些模块运行条件不同，风险也不同。地图预览错一幅图，可能让操作员选错路线；任意新增一个速度发布者，则可能让安全仲裁失效。若只按代码文件大小来决定重构范围，容易把低风险整理扩大成实机行为变化。

现有 bringup 提供 zlac 和 stm32 底盘后端分支；速度仲裁节点将导航、恢复和授权手动输入区分开。UI、手机与 AI 主要发任务或受限请求。独立视觉目录还包含已有未提交工作，不能因为“统一架构”就接入底盘。当前开发机是 Windows，没有现场设备、ROS 图或真实路线验收，因此本轮可证明的范围是本地源码和离线确定性逻辑。

要解决的问题不是重新发明一套分布式框架，而是让每条入口、数据流和控制责任能从文档追溯到现有实现；同时避免新文档把“源码有这个功能”写成“整车已经通过”。

## 决策

保留现有 ROS 包边界，并按职责划分驱动、状态估计、导航控制、任务交互、网络持久化和证据评估六层。各层通过已有 ROS 接口、HTTP 或文件契约连接。本文不会新增控制总线、统一消息代理或新的后台服务。

运动相关路径必须保留明确所有权。导航、恢复和手动输入不应分别绕过仲裁直达同一执行器；底盘后端不能同时控制同一车辆。最终发布者是否唯一，必须在实际启动模式中通过 ROS 图验证，不能仅凭一个节点的日志描述宣布成立。系统监督器拥有模式管理职责，不能用 HTTP 已接收代替 Nav2 已运行，更不能用模型生成的文字当任务成功证据。

独立感知只对自身输入输出负责。除非另有明确需求、安全审查和现场验收，不把识别结果自动转换成机械臂、Nav2 或底盘命令。视觉节点存在、相机有画面、检测准确和导航可使用检测是不同结论，应分别记录。

本轮仅修复离线特征评估中可复现的问题。驱动、CAN、串口、导航限速、机器人几何、MODEL-1/2/3 及启动流程保持不变。Agent 不启动实机、不发布速度、不切换生命周期；实际运动由现场人员执行。

## 考虑过的方案

方案一是把任务、桥接、巡逻和感知合并为一个大节点。这样调用链较短，但进程崩溃的影响面更大，也会耦合 UI、设备和网络依赖。合并无法自动解决控制权限和时序问题，反而让离线检查更困难，因此不采用。

方案二是由手机或 AI 直接调用最终速度话题，以减少中间状态。它绕过了现有控制边界，网络重发、过期输入或两个控制者抢占都可能产生意外行为，因此拒绝。

方案三是保持现有包结构，只明确接口和责任，并选择不会改变执行器行为的局部修复。它不能一轮解决所有历史问题，但变更可审查、可回退，符合当前证据条件，因此采纳。

## 收益、代价与已知限制

收益是可以按模块说明“谁生产、谁消费、谁决定执行、谁报告结果”。新成员先查仓库地图和集成规格，不必从所有启动脚本倒推架构。修改离线工具不再需要同时承担硬件重新标定的风险，已有视觉和地图工作也不会被无意覆盖。

代价是继续保留跨包状态同步、部分字符串负载和多个配置入口。文档不会消除这些复杂性，也不能替代 ROS 层的运行检查。包依赖声明只是构建入口之一，外部 SDK、动态启动和系统服务仍须单独核对。本轮不承诺自动检测全部重复发布者，也没有改变已有仲裁状态机。

## 验收与后续触发条件

离线检查只能验收本轮修改的确定性行为。目标机构建、传感器新鲜度、TF 唯一发布、地图路线绑定、控制所有权和真实停止效果均列入现场清单。任何无法关联到执行对象和时间的“成功”都保持未证明。

后续若需要多机器人、机械臂联动或新的远程控制入口，应先提交新的 ADR，写清控制优先级、失联策略、取消语义、急停边界和回滚方法，再进入实现。若发现本轮文档与实际运行链不符，优先修正文档中的事实描述并记录证据，不通过删除安全门槛来追求图上闭环。
